## Context

avalanche уже содержит клиент для исходящей нагрузки — remote-write
(`metricsgen/write.go`, `metricsgen/writev2.go`): HTTP-клиент с TLS,
tenant-заголовком, батчами и конкурентностью, запускаемый параллельно с
HTTP-сервером метрик через `oklog/run.Group` в `cmd/avalanche/avalanche.go`.
Query-нагрузка строится по тому же архитектурному паттерну, но:
дискретные запросы вместо батчей семплов, частота задаётся в QPS, а не
числом запросов/интервалом, и генерируемый контент — PromQL-строки, а не
`prompb.TimeSeries`. Мотивация — в proposal.md.

## Goals / Non-Goals

**Goals:**
- Дать управляемую по QPS и concurrency query-нагрузку (instant + range)
  на отдельный от remote-write целевой адрес.
- Переиспользовать существующую TLS/tenant инфраструктуру `write.go`
  вместо дублирования флагов.
- Сгенерировать разнообразный (шире, чем recording rules) набор
  PromQL-запросов поверх детерминированного списка имён метрик/labels.
- Не мешать существующим механизмам нагрузки (scrape, remote-write,
  rule-generation) при ошибках query-клиента.

**Non-Goals:**
- Проверка корректности результатов запросов (сравнение с ожидаемым
  значением) — только факт отправки/получения ответа, ошибки и латентность.
- Отдельная TLS/tenant-конфигурация для query API, отличная от
  remote-write — используется общая.
- Адаптивное управление нагрузкой (например, autotuning QPS по латентности
  ответов) — QPS статичен, задаётся флагом.
- Query load balancing/sharding по нескольким query API одновременно —
  один `--query-url` на процесс (для нескольких — несколько инстансов
  avalanche, как и для остальной нагрузки).

## Decisions

**1. Отдельный клиент `metricsgen/query.go`, симметричный `write.go`.**
Новый `Querier` содержит HTTP-клиент с тем же `buildTLSConfig` и той же
`tenantRoundTripper`/`userAgentRoundTripper` цепочкой, что и `Writer`
(переиспользуются существующие приватные функции/типы из `write.go` —
потребуется либо экспортировать их в пределах пакета `metricsgen`, либо
поднять в общий файл; они уже не экспортированы наружу пакета, так что
доступны напрямую внутри `metricsgen`).
- *Рассмотренная альтернатива*: полностью независимый HTTP-клиент без
  переиспользования TLS-кода. Отклонено — дублирование уже отлаженной
  логики (mTLS, tenant header, user-agent) без причины.

**2. QPS вместо "число запросов + интервал".**
В отличие от remote-write (`--remote-requests-count` +
`--remote-write-interval`), query-нагрузка задаётся напрямую в QPS
(`--query-instant-rate`, `--query-range-rate`), с бесконечным выполнением,
пока процесс жив (нет аналога "one-off" режима — query-нагрузка по
природе continuous, как правило дашбордов/API, а не разовая заливка).
Реализация: `time.Ticker` с периодом `time.Second / rate` на каждый вид
запроса (instant/range независимо), либо, при `rate` с дробной частью,
токен-бакет/накопитель для сохранения точного среднего QPS на длинных
интервалах.
- *Рассмотренная альтернатива*: единый общий QPS на оба вида запросов с
  долей range/instant. Отклонено по прямому запросу — два независимых
  QPS-флага проще включать/выключать по отдельности и не требуют
  дополнительной арифметики долей.

**3. Ограничение конкурентности — семафор на канал, как в `write.go`.**
`--query-concurrency` реализуется тем же паттерном, что
`concurrencyLimitCh := make(chan struct{}, concurrency)` в
`Writer.write()` — общий для instant и range запросов канал-семафор,
чтобы оба вида запросов совместно не превышали лимит одновременных
исходящих запросов.

**4. Пул PromQL-шаблонов готовится один раз при старте.**
`--query-template-count` шаблонов строится один раз (аналогично
`add-rule-generation`, но с более широким набором форм — см. Decision 5)
поверх той же детерминированной функции перечисления имён
метрик/labels, что вводится в `add-rule-generation` (см. proposal.md,
Impact). Во время работы процесса запросы выбираются случайно из
готового пула — не генерируются заново на каждый запрос (дешевле,
предсказуемее по форме нагрузки).
- *Рассмотренная альтернатива*: генерировать случайный PromQL на каждый
  запрос "на лету". Отклонено — дороже по CPU на каждый тик при высоком
  QPS и не даёт повторяемого набора форм для отладки/логов.

**5. Более широкий набор форм запросов, чем в rule-generation, — отдельный
генератор `querygen.go`.**
`add-rule-generation` генерирует шаблоны expr, ограниченные тем, что
допустимо в recording/alerting rule (по сути один PromQL-expr на правило,
без time-range семантики запроса). Query-load нужен более широкий каталог
форм, включая send-only-for-queries конструкции: bin-op между двумя
независимыми метриками (`metric_a / metric_b`), subquery
(`max_over_time(metric[1h:5m])`), явные time-range параметры (`start`,
`end`, `step` для range queries, которых у recording rules нет в принципе).
Поэтому это отдельный генератор, не обёртка над rulesgen.go — переиспользуется
только список имён метрик/labels, не сами expr-шаблоны.

**6. Обработка ошибок — логировать и продолжать, не прерывать процесс.**
Как и remote-write (`merr []error`, `w.logger.Error(...)`), ошибки
HTTP-запросов к query API логируются со счётчиком, но не останавливают
querier, scrape-сервер или remote-write — отдельная горутина/компонент
в `run.Group`, чьё завершение с ошибкой не должно приводить к остановке
всей программы теми же средствами, что уже используются для
remote-write (`g.Add(func() error {...}, func(error) { cancel() })`,
где ошибка querier'а обрабатывается отдельно от ошибки основного
HTTP-сервера).

## Risks / Trade-offs

- [Риск] Высокий суммарный QPS (`instant-rate + range-rate`) при низком
  `--query-concurrency` может привести к нарастающей очереди
  запросов (тики "копятся"), если query API отвечает медленнее, чем
  тикает генератор. → Митигация: неблокирующая постановка в очередь
  (аналогично `select { case concurrencyLimitCh <- struct{}{}: default:
  <дропнуть тик, залогировать> }` вместо блокирующей отправки в канал),
  чтобы генератор не накапливал бесконечно растущий backlog — поведение
  и это ограничение зафиксировать явным Non-Goal/Risk, а не отдельным
  requirement, так как точная стратегия backpressure — implementation
  detail.
- [Риск] `--query-range-window`/`--query-range-step`, дающие очень много
  точек в ответе (например, окно 30 дней с шагом 1с), могут создать
  чрезмерную нагрузку на query API за один запрос. → Митигация:
  документировать в `--help`/README типичные разумные диапазоны,
  ограничение числа точек не валидируется программно в этой версии
  (Non-Goal).
- [Trade-off] Переиспользование приватных TLS/tenant round-tripper'ов из
  `write.go` увеличивает связанность `query.go` и `write.go` внутри
  пакета `metricsgen` → приемлемо, оба уже в одном пакете, изменение не
  затрагивает публичный API пакета.
