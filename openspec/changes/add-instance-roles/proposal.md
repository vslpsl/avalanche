## Why

Один инстанс avalanche плохо масштабируется вертикально: `Collect()` и
кодирование `/metrics` однопоточны и синхронны (см. замеры в этой
беседе — 7.27с на scrape 1M серий, супралинейный рост памяти), а
remote-write, query-нагрузка (`add-query-load`) и генерация правил
(`add-rule-generation`) добавляют собственную нагрузку на тот же
процесс. Единственный способ масштабироваться — горизонтально, много
специализированных инстансов вместо одного универсального. Сейчас все
подсистемы (scrape-сервер, remote-write, querier, ruler) всегда
запускаются в одном процессе и активируются неявно через собственные
url/path-флаги (`--remote-url`, `--query-url`, `--rules-endpoint-path`), а
инстансы, генерирующие метрики, не могут поделить между собой единое
конфигурационное пространство серий без дублирования одинаковых имён.

## What Changes

- Добавляются флаги ролей инстанса — явные переключатели поверх
  существующих url/path-флагов: `--role-scrape-target`,
  `--role-remote-writer`, `--role-querier`, `--role-ruler` (bool, по
  умолчанию `true` у всех четырёх). Подсистема реально работает, только
  если её роль включена **и** её собственный триггер-флаг задан (`AND`,
  не `OR`) — то есть при дефолтных ролях поведение полностью совпадает с
  текущим (роль ничего не меняет, пока не выставлена в `false`).
  Выключение роли позволяет взять один общий конфиг (со всеми
  url/path-флагами) и раздать его инстансам, каждый из которых
  активирует только часть подсистем.
- Если ни `--role-scrape-target`, ни `--role-remote-writer` не включены
  — `Collector` не создаётся и не запускается вовсе (инстанс не тратит
  память/CPU на генерацию серий, которые ему не нужны, — актуально для
  чистых `querier`/`ruler` инстансов).
- Если `--role-scrape-target=false`, HTTP-хендлер `/metrics` не
  регистрируется (но `/health` остаётся всегда); если при этом
  `--role-remote-writer=true`, `Collector` всё равно создаётся и
  работает — его отдаёт `Gatherer` только remote-write клиенту, не HTTP.
- Добавляются флаги шардирования `--shard-index` (по умолчанию `0`) и
  `--shard-count` (по умолчанию `1`) для партиционирования генерации
  серий между несколькими `scrape-target`/`remote-writer` инстансами —
  **на уровне отдельных серий внутри метрики**: каждая метрика
  (gauge/counter/histogram/native-histogram/summary) существует на
  **всех** шардах одинаково (те же имена метрик везде), но внутри каждой
  метрики шард `i` инстанцирует только те `series_id`, для которых
  `series_id % shard_count == shard_index` — то есть каждый шард владеет
  своим непересекающимся подмножеством серий внутри общего диапазона
  `[0, series_count)`. Объединение всех шардов (`shard-index` от `0` до
  `shard-count-1`) с одинаковым остальным конфигом воспроизводит ровно
  тот же полный набор серий, что дал бы один нешардированный инстанс.
- `--shard-index`/`--shard-count` **не влияют** на роли `querier`/
  `ruler`: они всегда строят запросы/правила по полному
  конфигурационному набору метрик и серий, независимо от того, как
  шардирована генерация — так что нужно лишь небольшое число `querier`/
  `ruler` инстансов, не зависящее от числа `scrape-target`/
  `remote-writer` шардов.

## Capabilities

### New Capabilities
- `instance-roles`: явные флаги ролей инстанса
  (scrape-target/remote-writer/querier/ruler) поверх существующих
  триггер-флагов подсистем, плюс шардирование генерации серий
  (`--shard-index`/`--shard-count`) на уровне `series_id` внутри каждой
  метрики для горизонтального распределения нагрузки.

### Modified Capabilities
(нет)

## Impact

- Код: `cmd/avalanche/avalanche.go` (условный запуск `Collector`, HTTP
  `/metrics`, remote-write, querier, ruler по флагам ролей),
  `metricsgen/serve.go` (партиционирование итерации по `series_id` в
  `cycleValues`/`deleteValues`/`handleSeriesTicks`/`recreateMetrics` по
  `shard-index`/`shard-count`).
- **Связь с `add-partial-series-churn`** (implementation-level
  coupling): `churnGeneration []int32` и `churnPool []int32` из того
  изменения индексируются по `series_id` в диапазоне `[0,
  series_count)`. При включённом шардировании (`shard-count > 1`) эти
  структуры и вся churn-логика ДОЛЖНЫ строиться только над
  подмножеством `series_id`, которым владеет данный шард (`series_id %
  shard_count == shard_index`), а не над полным диапазоном — иначе шард
  будет считать incorrect "процент от полного series_count" вместо
  "процента от своей доли". Если `add-partial-series-churn` к моменту
  реализации этого изменения ещё не применён, реализовать
  шард-партиционирование сразу с учётом этого контракта.
- Соприкасается (implementation-level) с `add-query-load` и
  `add-rule-generation`: их HTTP/файловый клиент запускается только при
  соответствующей роли; их функции перечисления имён метрик/labels
  игнорируют `shard-index`/`shard-count` и всегда строятся по полному
  конфигурационному набору (подтверждено — Non-Goal шардирования для
  этих ролей, см. design.md).
- Не меняет wire-формат scrape/remote-write.

## Key decisions

1. **Форма флагов ролей**: 4 отдельных bool-флага
   (`--role-scrape-target`, `--role-remote-writer`, `--role-querier`,
   `--role-ruler`), каждый default `true`. Подтверждено пользователем.
2. **Гранулярность шардирования**: на уровне отдельных серий внутри
   метрики (`series_id % shard_count`), а не на уровне метрик-семейств.
   Подтверждено пользователем — точнее балансирует нагрузку между
   шардами, ценой связности с `add-partial-series-churn` (см. Impact).
3. **Querier/ruler и шардирование**: обе роли игнорируют
   `shard-index`/`shard-count`, всегда работают по полному
   конфигурационному набору метрик. Подтверждено пользователем
   (Recommended-опция).
