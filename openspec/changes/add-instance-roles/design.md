## Context

`cmd/avalanche/avalanche.go` сегодня всегда создаёт `Collector`, всегда
регистрирует `/metrics`, запускает remote-write только если
`--remote-url` задан, и отдаёт сгенерированные Prometheus-рулы
(`add-rule-generation`, уже реализовано) только если
`--rules-endpoint-path` задан (default `/rules`, то есть включено из
коробки). Все флаги сегодня задаются только через CLI — нет способа
передать один и тот же набор значений (кол-во метрик/серий/лейблов и
т.п.) многим инстансам без дублирования всей команды запуска в каждом
Deployment'е.

Первая версия этой спеки предлагала 4 независимых bool-флага ролей
(AND поверх существующих триггеров) + шардирование серий по
`series_id` между репликами одной роли. Пользователь скорректировал
требование: нужна ПРОСТАЯ модель "один флаг — один под — одна
подсистема, и ничего больше", без шардирования (отдельное, отложенное
изменение при необходимости).

## Goals / Non-Goals

**Goals:**
- Дать возможность запускать процесс в режиме ровно одной подсистемы
  (scrape-target / remote-writer / ruler), игнорируя триггер-флаги
  остальных, даже если они заданы в общем конфиге.
- Не тратить ресурсы (`Collector`, `/metrics`) на инстансах, которым
  они не нужны (в первую очередь — чистый `ruler`).
- Дать раздавать один и тот же конфиг (все флаги, кроме роли) через
  переменные окружения, без изменения `--role` не поменяв поведения
  по умолчанию.

**Non-Goals:**
- Шардирование генерации серий между репликами одной роли — явно
  исключено пользователем из этого изменения.
- Роль `querier` — подсистемы ещё нет (`add-query-load` не
  реализован), флаг `--role` её не принимает.
- Изменение поведения при `--role=""` (default) — во всех Goals/
  Non-Goals предполагается полная обратная совместимость.
- Config-файл (YAML/JSON) как отдельный механизм конфигурации —
  вместо него используется встроенная в `kingpin` поддержка
  env-переменных (см. Decision 2).

## Decisions

**1. Один эксклюзивный флаг `--role` (enum), а не несколько независимых
bool-флагов.**
Пользователь явно описал целевое поведение как "если роль задана —
работает ТОЛЬКО она", то есть взаимоисключающий выбор, а не независимые
переключатели. Один enum-флаг (`""`/`scrape-target`/`remote-writer`/
`ruler`) выражает это прямо, без необходимости валидировать недопустимые
комбинации нескольких bool'ов. Реализуется как `kingpin`
`EnumVar(&role, "", "scrape-target", "remote-writer", "ruler")`, по
аналогии с уже существующим `--series-operation-mode`
(`metricsgen/serve.go`).
- *Отклонённая альтернатива*: 4 независимых bool-флага
  (`--role-scrape-target` и т.п.) с AND-семантикой поверх триггер-флагов
  — это была первая версия спеки; отклонена пользователем как более
  сложная, чем нужно для целевого сценария.

**2. Общий конфиг через `kingpin.Application.DefaultEnvars()`, а не
самодельный `--config-file`.**
`gopkg.in/alecthomas/kingpin.v2` (уже прямая зависимость) умеет
проставить каждому зарегистрированному флагу дефолтный envar
`<AppName>_<FLAG_NAME>` одним вызовом
`kingpin.CommandLine.DefaultEnvars()` (после
`kingpin.CommandLine.Name = "avalanche"`), без единой правки в местах,
где сегодня регистрируются флаги (`metricsgen.NewConfigFromFlags`,
`metricsgen.NewWriteConfigFromFlags` — они получают `flagReg` как
`kingpin.Flag` и работают на том же `kingpin.CommandLine`). Явный
CLI-флаг всегда переопределяет env — стандартное поведение kingpin.
- Обязательное следствие: встроенные флаги `--help`/`--version`
  (созданы в `kingpin.New()`/`kingpin.Version()` без `.NoEnvar()`)
  тоже попали бы под `DefaultEnvars()` — `AVALANCHE_HELP=1`/
  `AVALANCHE_VERSION=1`, случайно оказавшиеся в общем `ConfigMap`,
  заставили бы каждый под, читающий этот `ConfigMap`, напечатать
  help/version и завершиться вместо запуска. Поэтому сразу после
  `DefaultEnvars()` нужно явно вызвать
  `kingpin.CommandLine.HelpFlag.NoEnvar()` и
  `kingpin.CommandLine.VersionFlag.NoEnvar()` — **не** через
  package-level `kingpin.HelpFlag`/`kingpin.VersionFlag` (это разные
  вещи: `kingpin.VersionFlag` — глобальная переменная, скопированная из
  `CommandLine.VersionFlag` во время инициализации пакета kingpin, то
  есть ДО того, как `main()` вызывает `kingpin.Version(...)` и реально
  создаёт `CommandLine.VersionFlag` — обращение к ней паникует на nil).
- Известное ограничение (не баг): повторяемый флаг `--const-label`
  (`StringsVar`) через env принимает несколько `label=value` пар только
  как одну строку с `\n`-разделителями, а не как несколько
  env-переменных/CSV — это поведение самого kingpin
  (`GetSplitEnvarValue`), документируется в README, не обходится кодом
  этого изменения.
- *Отклонённая альтернатива*: отдельный `--config-file` (YAML/JSON),
  который avalanche парсит сам. Отклонена пользователем — требует
  писать и поддерживать собственный парсер конфига и приоритет
  "флаг > файл > дефолт", тогда как `DefaultEnvars()` даёt то же самое
  за 4 строки поверх уже используемой библиотеки и естественно
  ложится на стандартный Kubernetes-паттерн `ConfigMap` → env vars.

**3. Порядок инициализации в `main()`: сначала решить роль, потом
опционально создать `Collector`.**
```go
doScrape := role == "" || role == "scrape-target"
doRemoteWrite := (role == "" || role == "remote-writer") && writeCfg.URL != nil
doRules := (role == "" || role == "ruler") && cfg.RulesEndpointPath != ""
needsCollector := doScrape || doRemoteWrite

if needsCollector {
    collector := metricsgen.NewCollector(*cfg)
    reg.MustRegister(collector)
    writeCfg.UpdateNotify = collector.UpdateNotifyCh()
    g.Add(collector.Run, collector.Stop)
}
// HTTP handler: /metrics только если doScrape; /health всегда;
// рулы только если doRules.
// remote-write только если doRemoteWrite.
```
При `role == ""` каждое `doX` в точности совпадает со старым условием
(`doScrape` всегда `true` — `/metrics` и раньше был безусловным;
`doRemoteWrite`/`doRules` совпадают с текущими `writeCfg.URL != nil`/
`cfg.RulesEndpointPath != ""`) — ноль регрессий для однопроцессного
использования без `--role`.
- *Рассмотренная альтернатива*: всегда создавать `Collector`, но не
  запускать его горутину. Отклонена — сам `NewCollector`/
  `recreateMetrics` уже выделяет память под все метрики; для чистого
  `ruler`-пода это именно та память, которую нужно не тратить (Goal).

**4. Валидация роли — явная ошибка при старте, а не тихий no-op.**
`--role=remote-writer` без `--remote-url` или `--role=ruler` без
`--rules-endpoint-path` — под, который ничего не делает, кроме
`/health`. Это почти наверняка ошибка конфигурации (перепутали
`--role`/забыли триггер-флаг) — `kingpin.FatalUsage` сразу при старте
понятнее, чем молча висящий под без ошибок в логах.

## Risks / Trade-offs

- [Риск] Оператор может по ошибке запустить несколько подов
  `scrape-target` с одним и тем же конфигом без какого-либо
  разделения серий между ними (шардирование сознательно вне scope) —
  все такие поды будут генерировать и отдавать ОДИН И ТОТ ЖЕ полный
  набор серий. Это ожидаемо (горизонтальное масштабирование через
  scrape-target реплики сегодня подразумевает избыточность/балансировку
  запросов, а не партиционирование данных) — документируется в README,
  не является дефектом этого изменения.
- [Trade-off] `--role=querier` не поддерживается до `add-query-load` —
  сознательно, чтобы не вводить флаг-заглушку без реальной подсистемы
  за ним.
