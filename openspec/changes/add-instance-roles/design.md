## Context

Сейчас `cmd/avalanche/avalanche.go` всегда создаёт `Collector`, всегда
регистрирует `/metrics`, и запускает remote-write только если
`--remote-url` задан (аналогично для query/rule-generation ролей из
`add-query-load`/`add-rule-generation`, каждая гейтится своим
url/path-флагом). Один процесс = один набор из `--series-count` серий на
метрику, без способа разделить это пространство между несколькими
процессами без коллизий имён. Мотивация — в proposal.md, включая замеры
однопоточности `Collect()`/scrape из более ранней части этой беседы.

## Goals / Non-Goals

**Goals:**
- Дать возможность выключать подсистемы (scrape-target/remote-writer/
  querier/ruler) независимо от их url/path-триггеров, чтобы один общий
  конфиг можно было раздать по специализированным инстансам.
- Не тратить ресурсы (Collector, HTTP `/metrics`) на инстансах, которым
  они не нужны.
- Дать шардирование генерации серий на уровне `series_id` внутри каждой
  метрики, с точной, проверяемой гарантией: объединение шардов равно
  нешардированному набору.
- Гарантировать совместимость шардирования с `add-partial-series-churn`
  (churn считается от доли шарда).

**Non-Goals:**
- Шардирование query/rule-нагрузки (`add-query-load`/
  `add-rule-generation`) — querier/ruler всегда работают по полному
  набору (подтверждённое решение).
- Автоматическое обнаружение/координация шардов (service discovery,
  распределённый consensus по `shard-count`) — числа `shard-index`/
  `shard-count` задаются оператором вручную/через шаблон деплоя (Helm,
  StatefulSet ordinal и т.п.), avalanche не проверяет, что все шарды
  реально запущены.
- Изменение поведения при `shard-count=1` (по умолчанию) — во всех
  Non-Goals и Goals предполагается, что это строго обратно совместимая
  надстройка.

## Decisions

**1. Роли — 4 независимых bool-флага, гейтящие вместе со своим
url/path-флагом (`AND`).**
`--role-X=true` (default) — необходимое, но не достаточное условие;
подсистема также требует своего триггер-флага, как и сейчас. Это значит:
при дефолтных ролях ничего не меняется. Выключение роли — чистый
дополнительный gate, а не замена существующей логики активации.
- *Рассмотренная альтернатива*: единый `--role` со списком через
  запятую. Отклонено пользователем — 4 явных bool-флага проще для
  kingpin (`BoolVar`) и консистентны со стилем остальных флагов
  avalanche.

**2. Порядок инициализации в `main()`: сначала решить, какие роли
активны, потом опционально создать `Collector`.**
```
needsCollector := *roleScrapeTarget || *roleRemoteWriter
if needsCollector {
    collector = metricsgen.NewCollector(cfg)
    reg.MustRegister(collector)
    g.Add(collector.Run, collector.Stop)
}
if *roleScrapeTarget {
    http.Handle("/metrics", promhttp.HandlerFor(reg, ...))
}
// /health регистрируется всегда, независимо от ролей
if *roleRemoteWriter && writeCfg.URL != nil { ... как сейчас ... }
if *roleQuerier && queryCfg.URL != nil { ... add-query-load ... }
if *roleRuler && rulesCfg.EndpointPath != "" { ... add-rule-generation ... }
```
- *Рассмотренная альтернатива*: всегда создавать `Collector`, но не
  запускать его горутину. Отклонено — сам `NewCollector`/`recreateMetrics`
  уже выделяет память под все метрики; при чистых querier/ruler ролях
  это именно та память, которую нужно не тратить (Goal).

**3. Шардирование — предикат `series_id % shard_count == shard_index`
в местах итерации по series_id.**
Единая точка: везде, где код сейчас делает `for idx := 0; idx <
s.seriesCount; idx++` (в `cycleValues`, `deleteValues`, и в
churn-логике из `add-partial-series-churn`), диапазон итерации меняется
на "только `idx`, для которых `idx % shard_count == shard_index`".
Реализуется как небольшой хелпер (например, итератор/предикат
`ownsSeriesID(idx int) bool`), используемый во всех этих местах, а не
дублирование модульной арифметики в каждом цикле.
- *Рассмотренная альтернатива*: партиционирование на уровне
  метрик-семейств (`metric_id % shard_count`), при котором каждая
  метрика целиком принадлежит одному шарду. Отклонено пользователем —
  партиционирование по `series_id` балансирует нагрузку точнее
  (особенно когда метрик-семейств мало, а `series_count` велик), хотя и
  требует протянуть шардирование через churn-логику (см. Decision 4).

**4. Churn (`add-partial-series-churn`) считает проценты и строит
`churnPool` только над series_id, принадлежащими шарду.**
`churnPool`/`churnGeneration` из `add-partial-series-churn`
инициализируются не над `[0, SeriesCount)`, а над отфильтрованным по
`ownsSeriesID` подмножеством этого диапазона (при `shard-count=1` это
эквивалентно полному диапазону — обратная совместимость сохраняется
автоматически, без специального кода под `shard-count=1`).
`windowTargetCount = floor(shard_owned_series_count *
PartialSeriesChurnPercent / 100)`, где `shard_owned_series_count` — размер
владеемого шардом подмножества (примерно `SeriesCount / shard_count`).
- *Рассмотренная альтернатива*: считать процент от полного
  `SeriesCount`, но физически churnить только пересечение с
  `ownsSeriesID`. Отклонено — при этом реальный процент,
  churnящийся в рамках шарда, был бы систематически ниже заданного (не
  соответствовал бы Requirement "Churn-percent считается от доли
  шарда").

**5. Querier/ruler используют `ownsSeriesID`-независимое, полное
перечисление.**
Функции перечисления имён метрик/labels из `add-rule-generation`
(tasks 2.1/2.2) и `add-query-load` не принимают `shard-index`/
`shard-count` вообще — они уже определены как чистые функции только от
`Config` (без учёта шардирования), так что дополнительных изменений в
них не требуется; querier/ruler роли просто не проходят через
`ownsSeriesID`.

## Risks / Trade-offs

- [Риск] Оператор может рассинхронизировать `shard-count` между
  разными инстансами одного "логического набора шардов" (например,
  часть с `shard-count=5`, часть — с `shard-count=10`) и получить
  пересекающиеся или неполные series_id — avalanche это не проверяет
  (Non-Goal: нет межпроцессной координации). → Митигация: документировать
  в README, что `shard-count` должен быть одинаков на всех инстансах
  одного набора; это ответственность деплой-шаблона (Helm values и
  т.п.), не самого avalanche.
- [Риск] Партиционирование по `series_id` (а не по метрикам) означает,
  что при большом `shard-count` и включённом `add-rule-generation`
  recording rule, ссылающееся на метрику целиком (`sum(metric)`),
  агрегирует данные, которые физически размазаны по нескольким
  scrape-target шардам — корректно только если все шарды пишутся в один
  target (remote-write) или скрейпятся одним Prometheus с общим
  federation/aggregation; чисто scrape-per-shard без remote-write в общий
  backend не даст единого агрегата. → Митигация: это ожидаемое свойство
  горизонтального шардирования (как в реальном Prometheus/Thanos), не
  дефект; явно отметить в README.
- [Trade-off] Партиционирование по `series_id` требует протянуть
  `ownsSeriesID`-фильтр через churn-логику `add-partial-series-churn`
  (Decision 4), в отличие от отклонённой альтернативы (партиционирование
  по метрикам), которая не требовала бы такой связности. Выбрано ради
  более точного баланса нагрузки между шардами — сознательный компромисс,
  подтверждённый пользователем.
