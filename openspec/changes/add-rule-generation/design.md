## Context

avalanche сейчас генерирует только сырые серии (`metricsgen/serve.go`) и
отдаёт их через scrape/remote-write. Нагрузка от rule evaluation engine
(recording + alerting rules) целевого Prometheus сейчас никак не
эмулируется и не автоматизируется — пользователю пришлось бы вручную
писать rules-файл, синхронизированный с именами метрик avalanche.
Значения серий также не воспроизводимы между запусками
(`rand.NewSource(time.Now().UnixNano())`), что мешает детерминированному
тестированию alerting rules. Мотивация подробнее — в proposal.md.

## Goals / Non-Goals

**Goals:**
- Сделать генерацию значений серий воспроизводимой через `--seed`.
- Зафиксировать контракт: имена метрик и ключи labels детерминированы
  относительно конфига (кроме явного переименования через
  `--metric-interval`).
- Сгенерировать при старте (опционально) и отдать по HTTP-эндпоинту YAML
  с Prometheus rule groups (recording + alerting), ссылающийся на реально
  сгенерированные метрики и стабильные ключи labels.
- Дать контроль над объёмом/формой правил через флаги (количество,
  размер группы, интервал вычисления).

**Non-Goals:**
- Автоматическая доставка/reload правил в целевой Prometheus —
  пользователь сам забирает содержимое эндпоинта (curl/скрипт/
  конфигурационная прослойка) и делает reload.
- Отслеживание переименования метрик (`--metric-interval`) и
  автоматическая перегенерация закешированного снапшота правил после
  старта.
- Произвольные пользовательские шаблоны выражений правил — в этой
  версии шаблоны фиксированы по типу метрики (gauge/counter/histogram/
  native histogram/summary), без языка кастомизации.
- Валидация сгенерированных правил через реальный Prometheus
  `promtool check rules` в рамках CI этого изменения (может быть добавлено
  отдельно).

## Decisions

**1. `--seed` с сентинелом `0` = поведение на основе времени.**
Нулевое значение сохраняет прежнее поведение без дополнительных условий.
`valGen` инициализируется `rand.NewSource(seed)`, если `seed != 0`, иначе
`rand.NewSource(time.Now().UnixNano())`, как сейчас.
- *Рассмотренная альтернатива*: считать `0` валидным пользовательским
  seed'ом и требовать отдельный флаг `--seed-enabled`. Отклонено —
  усложняет интерфейс ради редкого кейса (реальное желание использовать
  seed=0 как значение).

**2. Генерация правил — отдельный файл `metricsgen/rulesgen.go`, вызываемый
из `main()` до `g.Run()`, результат отдаётся по HTTP, а не пишется на
диск.**
Функция принимает уже сконструированный `Config` (тот же, что и
`Collector`) и список фактических имён метрик/ключей labels (детерминированно
выводимых из конфига теми же формулами, что и в `recreateMetrics`), и
строит структуру `ruleGroups` (собственные Go-структуры в
`rulesgen.go`, зеркалирующие формат Prometheus rule files — см. Risk
ниже про отказ от `github.com/prometheus/prometheus/model/rulefmt`),
затем сериализует её в YAML **один раз** и сохраняет результат как
байтовый снапшот
(`[]byte`) в замыкании простого HTTP-хендлера, зарегистрированного на
`--rules-endpoint-path` (если он не пуст; по умолчанию `/rules`) рядом с
`/metrics`/`/health` в `main()`. Хендлер на каждый запрос просто отдаёт
этот закешированный снапшот с `Content-Type: application/yaml` — без
повторной генерации.
- *Рассмотренная альтернатива*: писать YAML на диск по
  `--rules-output-path` и просить пользователя подключить файл через
  `rule_files:`. Отклонено по прямому запросу пользователя — HTTP-эндпоинт
  не требует общего volume/файловой системы между avalanche и целевым
  Prometheus (или прослойкой конфигурации, которая эти правила заберёт),
  что упрощает деплой в контейнеризированных средах.
- *Рассмотренная альтернатива*: пересчитывать YAML на каждый GET-запрос.
  Отклонено — генерация чисто детерминирована конфигом и не меняется в
  течение жизни процесса (см. Decision 4), пересчёт на каждый запрос был
  бы тратой CPU без функциональной пользы; кеширование снапшота в памяти
  проще и дешевле.
- *Рассмотренная альтернатива*: генерировать правила "на лету" по мере
  создания метрик внутри `Collector`. Отклонено — усложнило бы `Collector`
  несвязанной ответственностью; генерация правил нужна один раз при
  старте и не требует доступа к мутируемому состоянию коллектора.

**2а. Дефолт `--rules-endpoint-path` — `/rules` (включено из коробки),
а не пустая строка.**
В отличие от более ранней итерации (флаг-триггер с пустым дефолтом),
эндпоинт теперь зарегистрирован по умолчанию — при
`--recording-rule-count=0`/`--alerting-rule-count=0` (тоже дефолты) он
просто отдаёт валидный `groups: []`. `--rules-endpoint-path=""` остаётся
явным способом отключить регистрацию эндпоинта целиком.
- *Рассмотренная альтернатива*: оставить дефолт пустым (opt-in), либо
  сделать эндпоинт безусловным без флага пути вовсе. Отклонено по
  прямому запросу пользователя — непустой дефолт даёт разумное поведение
  "из коробки" (согласуется с тем, что `--role-ruler` в
  `add-instance-roles` тоже включён по умолчанию), но путь остаётся
  настраиваемым и отключаемым, в отличие от жёстко зашитого `/rules`.

**3. Шаблоны выражений — фиксированные по типу метрики.**
- gauge → recording: `sum by (<label>) (<metric>)`
- counter → recording: `sum by (<label>) (rate(<metric>[5m]))`
- classic histogram → recording:
  `histogram_quantile(0.99, sum by (le, <label>) (rate(<metric>_bucket[5m])))`
- native histogram → recording:
  `histogram_quantile(0.99, sum by (<label>) (rate(<metric>[5m])))`
- summary → recording: `avg by (<label>) (<metric>{quantile="0.5"})`
- alerting: строится поверх случайно выбранного recording-выражения (или
  напрямую метрики, если recording rules не запрошены) вида
  `<expr> > <порог>`, где порог — эвристика по типу (например, gauge:
  фиксированный порог 80, учитывая что значения генерируются в диапазоне
  `[0, 100)`, см. `cycleValues`).
`<label>` каждый раз выбирается детерминированно (по индексу правила по
модулю числа сконфигурированных label-ключей) из уже существующих
`label_key_...` — не изобретаются новые ключи.
- *Рассмотренная альтернатива*: случайный выбор произвольных PromQL
  конструкций. Отклонено — непредсказуемая нагрузка и риск синтаксически
  некорректных правил; фиксированные шаблоны по типу проще
  верифицировать и достаточно реалистичны для нагрузочного теста.

**4. Закешированный снапшот строится один раз, без слежения за churn'ом.**
Поскольку recording/alerting rules ссылаются только на имя метрики и
ключи labels (не на конкретные `series_id`/`cycle_id`), обычный series
churn (включая `--partial-series-churn-percent` из
`add-partial-series-churn`) не инвалидирует уже закешированный снапшот —
правила продолжают работать над тем же именем метрики независимо от
того, какие конкретные серии внутри неё churnятся. Только
`--metric-interval` (переименование метрики целиком) ломает эту
стабильность — фиксируется как Non-Goal, а не как баг.

**5. Правила группируют/фильтруют только по собственным меткам avalanche
— независимость от числа реплик с одинаковым конфигом.**
Целевой сценарий: в кластере несколько подов avalanche с ИДЕНТИЧНЫМ
конфигом работают как scrape-target/remote-writer (различаются только
внешней меткой вроде `pod`, добавляемой Prometheus при
scrape/relabeling, а не самим avalanche), и пишут в один целевой
Prometheus. Генератор правил строит `by (<label>)`/`{...}` только над
метками из `c.labelKeys` (собственные `label_key_...` avalanche) и
никогда не ссылается на `pod`/`instance`/`job` или любые другие метки,
добавляемые извне механизмом scrape. Поэтому:
- количество сгенерированных правил и их выражения зависят только от
  `Config` (счётчики типов метрик, `--label-count` и т.п.), а не от
  числа запущенных реплик;
- сами выражения (`sum by (<label>) (...)` и т.п.) корректно агрегируют
  данные независимо от того, сколько реплик фактически писало в целевой
  Prometheus — группировка не по `pod`/`instance` означает, что серии от
  всех реплик естественно попадают в один агрегат.
- *Рассмотренная альтернатива*: параметризовать генератор числом реплик
  (например, домножать пороги в alerting rules на ожидаемое число
  подов). Отклонено — avalanche-ruler не обязан знать, сколько реплик
  запущено в кластере (это решение уровня деплоя/Helm, не конфига
  avalanche); правила и так работают корректно благодаря отсутствию
  группировки по внешним меткам, никакого домножения не требуется.

## Risks / Trade-offs

- [Риск] Пороговые значения в alerting rules (эвристика по диапазону
  генерируемых значений) могут не совпадать с реальными "интересными"
  значениями пользователя и либо никогда не сработают, либо будут
  константно firing. → Митигация: документировать эвристику в `--help` и
  в README, пороги — начальная точка для ручной подстройки пользователем,
  не гарантия "осмысленного" алерта.
- [Риск] При очень большом числе сконфигурированных метрик (100k+ серий,
  но метрик-*семейств* обычно на 2-3 порядка меньше) и большом
  `--recording-rule-count`/`--alerting-rule-count` ответ эндпоинта может
  запросить больше правил, чем реально существует уникальных
  метрик-семейств.
  → Митигация: генератор ДОЛЖЕН ограничивать число правил числом
  доступных метрик-семейств (не может сгенерировать больше recording
  rules, чем есть уникальных метрик), см. соответствующий task с
  проверкой в tasks.md.
- [Риск, проверено на практике] `github.com/prometheus/prometheus/model/rulefmt`
  на бумаге выглядел как "уже транзитивная зависимость, без доп. цены"
  (см. первую версию этого документа), но фактически импортирует полный
  PromQL query engine (нужен для валидации annotation-шаблонов) и тянет
  за собой ~30 новых indirect-модулей, включая `k8s.io/client-go` и
  OpenTelemetry — измерено: **+6.8MB (+35%) к размеру бинаря** ради пары
  структур для сериализации YAML. avalanche до этого изменения
  сознательно использовал из `prometheus/prometheus` только маленький
  самодостаточный пакет `prompb`. → **Решение изменено**: вместо
  `rulefmt.RuleGroups`/`rulefmt.Rule` генератор использует собственные,
  вручную объявленные Go-структуры (`ruleGroups`/`ruleGroup`/`rule` в
  `metricsgen/rulesgen.go`) с теми же yaml-тегами, что зеркалируют
  публичный, стабильный формат Prometheus rule files 1:1, без
  зависимости от самого пакета `rulefmt`. Сериализация — тем же
  `go.yaml.in/yaml/v3`, что уже транзитивно тянется в проект (просто
  переводится из indirect в прямую зависимость, без новых модулей).
  Для тестовой проверки валидности вывода `promql/parser` тоже не
  подходит — несмотря на кажущуюся лёгкость, его `ast.go` импортирует
  `github.com/prometheus/prometheus/storage`, которая тянет `tsdb` и те
  же тяжёлые транзитивные зависимости (проверено на практике тем же
  способом). Тесты проверяют вывод через round-trip в собственную
  `ruleGroups` (десериализация обратно) и точечные строковые проверки
  `expr` (например, отсутствие висячей запятой в `by (le, )`), без
  привлечения какого-либо PromQL-парсера.
