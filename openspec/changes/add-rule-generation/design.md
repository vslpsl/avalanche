## Context

avalanche сейчас генерирует только сырые серии (`metricsgen/serve.go`) и
отдаёт их через scrape/remote-write. Нагрузка от rule evaluation engine
(recording + alerting rules) целевого Prometheus сейчас никак не
эмулируется и не автоматизируется — пользователю пришлось бы вручную
писать rules-файл, синхронизированный с именами метрик avalanche.
Значения серий также не воспроизводимы между запусками
(`rand.NewSource(time.Now().UnixNano())`), что мешает детерминированному
тестированию alerting rules. Мотивация подробнее — в proposal.md.

## Goals / Non-Goals

**Goals:**
- Сделать генерацию значений серий воспроизводимой через `--seed`.
- Зафиксировать контракт: имена метрик и ключи labels детерминированы
  относительно конфига (кроме явного переименования через
  `--metric-interval`).
- Сгенерировать при старте (опционально) файл Prometheus rule groups
  (recording + alerting), ссылающийся на реально сгенерированные метрики
  и стабильные ключи labels.
- Дать контроль над объёмом/формой правил через флаги (количество,
  размер группы, интервал вычисления).

**Non-Goals:**
- Автоматическая доставка/reload файла правил в целевой Prometheus —
  пользователь сам подключает `rule_files:` и делает reload.
- Отслеживание переименования метрик (`--metric-interval`) и
  автоматическая перегенерация файла правил после старта.
- Произвольные пользовательские шаблоны выражений правил — в этой
  версии шаблоны фиксированы по типу метрики (gauge/counter/histogram/
  native histogram/summary), без языка кастомизации.
- Валидация сгенерированных правил через реальный Prometheus
  `promtool check rules` в рамках CI этого изменения (может быть добавлено
  отдельно).

## Decisions

**1. `--seed` с сентинелом `0` = поведение на основе времени.**
Нулевое значение сохраняет прежнее поведение без дополнительных условий.
`valGen` инициализируется `rand.NewSource(seed)`, если `seed != 0`, иначе
`rand.NewSource(time.Now().UnixNano())`, как сейчас.
- *Рассмотренная альтернатива*: считать `0` валидным пользовательским
  seed'ом и требовать отдельный флаг `--seed-enabled`. Отклонено —
  усложняет интерфейс ради редкого кейса (реальное желание использовать
  seed=0 как значение).

**2. Генерация правил — отдельный файл `metricsgen/rulesgen.go`, вызываемый
из `main()` до `g.Run()`.**
Функция принимает уже сконструированный `Config` (тот же, что и
`Collector`) и список фактических имён метрик/ключей labels (детерминированно
выводимых из конфига теми же формулами, что и в `recreateMetrics`), и
строит структуру `rulefmt.RuleGroups` (использует существующий пакет
`github.com/prometheus/prometheus/model/rulefmt`, уже транзитивная
зависимость через `github.com/prometheus/prometheus`), затем сериализует
её в YAML и пишет на диск.
- *Рассмотренная альтернатива*: генерировать правила "на лету" по мере
  создания метрик внутри `Collector`. Отклонено — усложнило бы `Collector`
  несвязанной ответственностью; генерация правил нужна один раз при
  старте и не требует доступа к мутируемому состоянию коллектора.

**3. Шаблоны выражений — фиксированные по типу метрики.**
- gauge → recording: `sum by (<label>) (<metric>)`
- counter → recording: `sum by (<label>) (rate(<metric>[5m]))`
- classic histogram → recording:
  `histogram_quantile(0.99, sum by (le, <label>) (rate(<metric>_bucket[5m])))`
- native histogram → recording:
  `histogram_quantile(0.99, sum by (<label>) (rate(<metric>[5m])))`
- summary → recording: `avg by (<label>) (<metric>{quantile="0.5"})`
- alerting: строится поверх случайно выбранного recording-выражения (или
  напрямую метрики, если recording rules не запрошены) вида
  `<expr> > <порог>`, где порог — эвристика по типу (например, gauge:
  фиксированный порог 80, учитывая что значения генерируются в диапазоне
  `[0, 100)`, см. `cycleValues`).
`<label>` каждый раз выбирается детерминированно (по индексу правила по
модулю числа сконфигурированных label-ключей) из уже существующих
`label_key_...` — не изобретаются новые ключи.
- *Рассмотренная альтернатива*: случайный выбор произвольных PromQL
  конструкций. Отклонено — непредсказуемая нагрузка и риск синтаксически
  некорректных правил; фиксированные шаблоны по типу проще
  верифицировать и достаточно реалистичны для нагрузочного теста.

**4. Файл правил пишется один раз, без слежения за churn'ом.**
Поскольку recording/alerting rules ссылаются только на имя метрики и
ключи labels (не на конкретные `series_id`/`cycle_id`), обычный series
churn (включая `--partial-series-churn-percent` из
`add-partial-series-churn`) не
инвалидирует уже записанный файл правил — правила продолжают работать
над тем же именем метрики независимо от того, какие конкретные серии
внутри неё churnятся. Только `--metric-interval` (переименование метрики
целиком) ломает эту стабильность — фиксируется как Non-Goal, а не как
баг.

## Risks / Trade-offs

- [Риск] Пороговые значения в alerting rules (эвристика по диапазону
  генерируемых значений) могут не совпадать с реальными "интересными"
  значениями пользователя и либо никогда не сработают, либо будут
  константно firing. → Митигация: документировать эвристику в `--help` и
  в README, пороги — начальная точка для ручной подстройки пользователем,
  не гарантия "осмысленного" алерта.
- [Риск] При очень большом числе сконфигурированных метрик (100k+ серий,
  но метрик-*семейств* обычно на 2-3 порядка меньше) и большом
  `--recording-rule-count`/`--alerting-rule-count` файл правил может
  оказаться больше, чем реально существует уникальных метрик-семейств.
  → Митигация: генератор ДОЛЖЕН ограничивать число правил числом
  доступных метрик-семейств (не может сгенерировать больше recording
  rules, чем есть уникальных метрик), см. соответствующий task с
  проверкой в tasks.md.
- [Trade-off] Использование `rulefmt` из `github.com/prometheus/prometheus`
  (уже транзитивная зависимость) вместо ручной сборки YAML-структур —
  чуть больше связанности с версией Prometheus в go.mod, но гарантирует
  соответствие реальному формату rule_files и валидацию через
  `rulefmt.Parse`.
