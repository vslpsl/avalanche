## Purpose

Отдаёт по HTTP-эндпоинту Prometheus rule groups (recording rules и
alerting rules), соответствующие текущей конфигурации генерации метрик
avalanche, чтобы можно было воспроизвести на целевом Prometheus нагрузку
от rule evaluation engine, а не только от scrape/remote-write.
Дополнительно делает генерацию значений серий воспроизводимой через явный
seed.

## ADDED Requirements

### Requirement: Флаг seed для воспроизводимой генерации значений
Система ДОЛЖНА (SHALL) предоставлять флаг `--seed` (int64, по умолчанию
`0`). При `--seed=0` генератор значений ДОЛЖЕН (SHALL) использовать
источник на основе текущего времени, как и раньше. При ненулевом
`--seed` генератор значений ДОЛЖЕН (SHALL) быть инициализирован этим
значением, так что последовательность генерируемых значений серий
одинакова между запусками с одинаковым конфигом.

#### Scenario: Одинаковый seed даёт одинаковые значения
- **WHEN** avalanche запущен дважды с одинаковым конфигом и одинаковым
  `--seed=42`
- **THEN** последовательности значений (Set/Add/Observe) серий совпадают
  между двумя запусками

#### Scenario: Seed по умолчанию не меняет прежнее поведение
- **WHEN** avalanche запущен без `--seed` (значение по умолчанию `0`)
- **THEN** генератор значений использует источник на основе времени, как
  до этого изменения

### Requirement: Стабильность имён метрик и ключей labels
Имена метрик и ключи labels (например, `label_key_<...>_<idx>`) ДОЛЖНЫ
(SHALL) полностью выводиться из конфигурации запуска (счётчики типов
метрик, `--label-count`, `--metricname-length`, `--labelname-length`,
`--const-label`) и оставаться неизменными на протяжении жизни процесса,
за исключением явного переименования через `--metric-interval`. Значения
`series_id` и `cycle_id` НЕ ДОЛЖНЫ (SHALL NOT) считаться частью этого
контракта стабильности — они могут меняться в результате churn'а серий.

#### Scenario: Одинаковый конфиг даёт одинаковый набор имён и ключей labels
- **WHEN** avalanche запускается дважды с идентичным конфигом
- **THEN** множество имён метрик и множество ключей labels (без учёта
  `series_id`/`cycle_id`) идентично между запусками

### Requirement: Флаг пути HTTP-эндпоинта с правилами
Система ДОЛЖНА (SHALL) предоставлять флаг `--rules-endpoint-path`
(строка, по умолчанию `/rules`). Если флаг пуст (явно задан как `""`),
эндпоинт с правилами НЕ ДОЛЖЕН (SHALL NOT) регистрироваться и поведение
avalanche НЕ ДОЛЖНО (SHALL NOT) меняться относительно текущего. Если
флаг не пуст (включая значение по умолчанию `/rules`), avalanche
ДОЛЖЕН (SHALL) до начала обслуживания `/metrics` построить YAML в формате
Prometheus rule groups (`groups: [...]`) и зарегистрировать на указанном
пути GET-обработчик, отдающий этот YAML с заголовком
`Content-Type: application/yaml`.

#### Scenario: Флаг по умолчанию — эндпоинт включён на /rules
- **WHEN** avalanche запущен без явного указания `--rules-endpoint-path`
- **THEN** эндпоинт зарегистрирован на `/rules` и отвечает на `GET /rules`
  (пустым `groups: []`, если `--recording-rule-count` и
  `--alerting-rule-count` тоже не заданы)

#### Scenario: Флаг явно пуст — эндпоинт отключён
- **WHEN** avalanche запущен с `--rules-endpoint-path=""`
- **THEN** эндпоинт с правилами не регистрируется, запрос по любому
  дополнительному пути не связан с генерацией правил

#### Scenario: Флаг задан — эндпоинт отдаёт валидный YAML
- **WHEN** avalanche запущен с `--rules-endpoint-path=/rules` и выполняется
  `GET /rules`
- **THEN** ответ имеет `Content-Type: application/yaml` и тело — валидный
  YAML, структурно соответствующий формату Prometheus rule groups
  (`groups: [{name, interval, rules: [{record/alert, expr, for, labels,
  annotations}]}]`)

### Requirement: Recording rules по сгенерированным метрикам
Система ДОЛЖНА (SHALL) предоставлять флаг `--recording-rule-count` (целое
число, по умолчанию `0`), задающий число recording rules для генерации.
Каждое сгенерированное recording rule ДОЛЖНО (SHALL) ссылаться на имя
одной из сгенерированных метрик и использовать выражение, соответствующее
её типу (например, `sum by (<label>) (...)` для gauge/counter с `rate()`
для counter, `histogram_quantile(...)` для histogram/native histogram).

#### Scenario: Recording rules не генерируются по умолчанию
- **WHEN** avalanche запущен без `--recording-rule-count` (по умолчанию
  `0`)
- **THEN** ответ эндпоинта (если включён) не содержит recording rules

#### Scenario: Recording rules соответствуют типу метрики
- **WHEN** `--recording-rule-count=10` и среди сгенерированных метрик
  есть classic histogram
- **THEN** хотя бы одно recording rule для этой метрики использует
  `histogram_quantile` над `rate(<metric>_bucket[...])`

### Requirement: Alerting rules по сгенерированным метрикам
Система ДОЛЖНА (SHALL) предоставлять флаг `--alerting-rule-count` (целое
число, по умолчанию `0`), задающий число alerting rules для генерации.
Каждое сгенерированное alerting rule ДОЛЖНО (SHALL) содержать `alert`,
`expr` (пороговое условие над сгенерированной метрикой или recording
rule), `for` и непустые `labels`/`annotations`.

#### Scenario: Alerting rules не генерируются по умолчанию
- **WHEN** avalanche запущен без `--alerting-rule-count` (по умолчанию
  `0`)
- **THEN** ответ эндпоинта (если включён) не содержит alerting rules

#### Scenario: Alerting rule содержит обязательные поля
- **WHEN** `--alerting-rule-count=5`
- **THEN** каждое сгенерированное alerting rule содержит непустые
  `alert`, `expr`, `for`, `labels`, `annotations`

### Requirement: Группировка и интервал вычисления правил
Система ДОЛЖНА (SHALL) предоставлять флаги `--rule-group-size` (целое
число, по умолчанию `10`) и `--rule-eval-interval` (секунды, по умолчанию
`60`). Сгенерированные rules ДОЛЖНЫ (SHALL) быть распределены по группам
не более чем по `rule-group-size` правил в каждой, и каждая группа ДОЛЖНА
(SHALL) иметь `interval`, равный `--rule-eval-interval`.

#### Scenario: Правила распределены по группам заданного размера
- **WHEN** `--recording-rule-count=25`, `--rule-group-size=10`
- **THEN** сгенерировано 3 группы с 10, 10 и 5 правилами соответственно

### Requirement: Ответ эндпоинта не обновляется автоматически после старта
YAML-снапшот, отдаваемый по `--rules-endpoint-path`, СТРОИТСЯ (SHALL) один
раз при старте и кешируется в памяти; последующие запросы к эндпоинту
НЕ ДОЛЖНЫ (SHALL NOT) вызывать пересборку и НЕ ДОЛЖНЫ (SHALL NOT)
отражать последующие изменения состояния (churn серий, смена значений).
Если активен `--metric-interval` (переименование метрик), система
НЕ ДОЛЖНА (SHALL NOT) гарантировать, что закешированный снапшот
продолжает ссылаться на существующие имена метрик после переименования.

#### Scenario: Ответ эндпоинта не меняется в течение работы процесса
- **WHEN** avalanche работает с `--rules-endpoint-path` и активным
  churn'ом серий (`--series-interval`/`--partial-series-churn-percent`),
  и эндпоинт запрашивается несколько раз подряд
- **THEN** тело ответа идентично между всеми запросами и не меняется
  после первоначального построения снапшота при старте

### Requirement: Независимость от количества реплик с одинаковым конфигом
Генерация правил ДОЛЖНА (SHALL) зависеть только от конфигурации
генерации метрик (`Config`) и НЕ ДОЛЖНА (SHALL NOT) зависеть от того,
сколько реплик avalanche с идентичным конфигом развёрнуто и пишет в
целевой Prometheus (например, несколько подов-scrape-target/
remote-writer, различаемых внешней меткой вроде `pod`, добавляемой
Prometheus при scrape/relabeling). Выражения recording и alerting rules
ДОЛЖНЫ (SHALL) группировать и фильтровать данные только по собственным
меткам avalanche (ключи из `--label-count`/`--const-label`), и НЕ ДОЛЖНЫ
(SHALL NOT) ссылаться на внешние метки вроде `pod`, `instance` или `job`,
которые avalanche не контролирует.

#### Scenario: Число реплик не влияет на сгенерированные правила
- **WHEN** правила генерируются для одного и того же `Config` независимо
  от того, разворачивается ли одна реплика avalanche или несколько с тем
  же конфигом
- **THEN** число сгенерированных правил, их группировка по группам и все
  выражения идентичны в обоих случаях

#### Scenario: Выражения не ссылаются на внешние метки
- **WHEN** генерируется любое recording или alerting rule
- **THEN** его `expr` не содержит фильтров или группировки по меткам
  `pod`, `instance` или `job`
